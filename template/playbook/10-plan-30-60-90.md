# 10 — The first 90 days

## The shape

Three months, three jobs:

| Month | The job | Success looks like |
|---|---|---|
| **1** | Prove the machine works and one person wants the product | One narrow slice shipped, used by one real person who paid |
| **2** | Find the repeatable loop | You know which channel brings users, and the machine runs the daily loop without you |
| **3** | Decide whether this is a company or an experiment | Revenue, or a clear reason to stop |

The biggest mistake is spending month 1 on the machine and month 3 on the
market. **Month 1 must include a real user.**

---

## Month 1 — build the machine and one customer

### Week 1: the problem, the charter, the repo

| Day | Do | Done when |
|---|---|---|
| 1 | Write the problem statement (§07) | you can name a specific person with a specific painful job |
| 2 | Write `company/charter.md` | a stranger could judge a feature against it |
| 3 | `node tooling/src/cli.mjs init`, create the repo, set the budget ceilings | `company/budget.md` has your numbers; tools have hard caps |
| 4 | Pick the stack; create the accounts | CI runs green on an empty repo; the six vendors are live |
| 5 | Set the agent permissions and the daily/weekly schedules | the agent cannot reach production, billing, or a customer's inbox |
| 6 | Write the first spec with numbered ACs | a QA agent could write failing tests without asking you a question |
| 7 | Decompose into tasks; set write scopes | `node tooling/src/cli.mjs board --ready` shows work |

**Do not skip the charter.** It is 30 minutes now and it is the difference
between an agent team that converges and one that produces six different
products.

### Week 2: build one narrow slice

- One deployable. One flow. **One thing the user pays for.**
- The spec has 5–8 acceptance criteria, numbered `AC-1`…`AC-n`.
- Decompose into 5–10 tasks, each independently verifiable.
- Run the pipeline end to end: implement → test → review → preview deploy.
- **You click the feature yourself, on a real device, at least three times.**

The failure mode to watch: the agent produces a technically complete feature
that solves a problem you have not validated. Guard it with the rule in
`playbook/03-pipeline.md`: **no task starts until the spec is approved**, and
the spec starts with a problem, not a solution.

### Week 3: get it in front of one person

- Find one person who has the problem — a friend, a former colleague, someone
  from a community you actually participate in.
- Watch them use it. **Do not explain anything.** Write down every point where
  they hesitate, because that is your roadmap.
- Do not build anything during this session.
- Afterward: file their confusion as tasks. The gap between what you built
  and what they understood is the most valuable data you will get this month.

**If they do not pay** (or would not pay if you asked), stop and fix the
problem statement. Do not add features.

### Week 4: make the loop automatic

- Set up the daily and weekly schedules (`playbook/11-running-it-in-dsh.md`).
- Run `node tooling/src/cli.mjs doctor` weekly and fix what it reports.
- Write the first ADR (`node tooling/src/cli.mjs new adr "..."`).
- Publish something: a short post about what you are building. **Post early.**
  The point is not reach; it is to start the habit and to make the work public
  so it can be improved.
- Set the **kill line** with a date.

**Month 1 done when:** one person uses the product and one person pays, or
you have a dated, written reason to stop.

## Month 2 — find the loop

### The three questions of month 2

1. **Which channel brings people?** Test two, not five. A community you are
   already in, and direct outreach to a list you built.
2. **Do they activate?** The percentage who reach first value. If activation
   is low, the problem is the product, not the marketing.
3. **Does the machine run without me?** One full week where you touched the
   board only twice a day.

### The weekly loop

| Day | Human time | Machine |
|---|---|---|
| Monday | 30 min: read the metrics, write one direction sentence | — |
| Daily | 10 min: read the board, decide escalations | implement, test, review, deploy, triage support |
| Friday | 45 min: read one research brief, write one direction sentence, delete one thing | — |

### What to add in month 2

- **Metrics and a dashboard.** The twelve numbers in `company/metrics.md`. The
  activation metric is the one that matters.
- **A support loop.** The in-app feedback button. File every repeated question
  as a task the same day.
- **The second feature** — the one your first user asked for twice.
- **The kill-line check.** Are you on track to the date? If not, decide now:
  change the date, change the product, or stop. Do not let it drift.

### What NOT to add in month 2

- A second product.
- A mobile app (unless a user asked for it twice).
- A second queue, a second datastore, or a microservice.
- SOC 2.
- Paid ads before the activation rate is good.

## Month 3 — decide

### Month 3 is a decision month, not a build month

The job of month 3 is to answer three questions with evidence:

1. **Is there demand?** Not "people liked it" — a number. Users, paid
   conversions, retention at week 4.
2. **Does the machine work?** Your review minutes per merged change. Your
   token spend per merged change. Whether the daily loop runs without you.
3. **Can this be a business?** At the current ARPA, how many customers do you
   need for the model to work, and can you reach them?

### The four outcomes

| Outcome | Signal | Action |
|---|---|---|
| **It works** | paying users, retention, the loop runs without you | double down: narrow further, raise prices, keep the machine |
| **Product works, distribution doesn't** | users love it, you can't find more | fix distribution: one channel, ten weeks, hard. This is the most common survivable failure |
| **Machine works, product doesn't** | the agent team is fine, nobody wants it | stop. Write the post-mortem. **FacelessForge's public kill line is the model here** |
| **Neither works** | the loop needs you constantly and users don't care | stop, and publish what you learned. The 8% success rate is real; the failures are worth publishing |

### Month 3 deliverables

- A written review: what shipped, what it cost, what the metrics say.
- The roadmap for the next quarter — or the decision to stop.
- An updated charter if the product's shape changed.
- **The system is now reusable.** The next product skips month 1 entirely: the
  company OS, the roles, the gates, the schedules, the budget all carry over.
  That is where the 80% starts paying.

## The rituals that make it work

### Daily (10 minutes)

```sh
node tooling/src/cli.mjs doctor        # is the machine healthy?
node tooling/src/cli.mjs board         # what moved, what is stuck
node tooling/src/cli.mjs board --ready
```

Read the escalations. Answer each in one line.

### Weekly (45 minutes)

1. Read `company/metrics.md` — the twelve numbers.
2. Read what shipped. What surprised you?
3. Write **one direction sentence** into `company/roadmap.md`.
4. Read one research brief.
5. **Delete one thing.** A feature, a flag, a dependency, a metric, a plan.

Step 5 is the one people skip, and it is the one that keeps the company from
becoming an archaeological dig.

### Monthly (2 hours)

- Read the budget against the ceilings.
- Read the incident history and the support tickets.
- Update the charter if the company has changed.
- Check the risk register (`playbook/09-risks.md`).

## The five numbers that matter in month 1

| Number | Target | Why |
|---|---|---|
| **Time from idea to working feature** | < 1 day | this is the thing AI actually buys you |
| **Your review minutes per merged change** | falling | the real cost of the machine |
| **Cost per merged change** | falling | model + infra, divided by merged PRs |
| **Activation rate** | > 40% | users who reach first value |
| **Paying users** | ≥ 1 by day 30 | the only number that proves the 20% |

If the first two improve and the fifth does not, you have built a faster way
to make something nobody wants. That is the most common outcome, and it is why
the kill line exists.

## The failure modes of the first 90 days

| Failure | What it looks like | Prevention |
|---|---|---|
| **Machine-first** | three weeks of tooling, no user | the week-3 user test is non-negotiable |
| **Feature-first** | 40 tasks before anyone used it | the charter's "out of scope" section, and the human approval gate |
| **The agent runs away** | 60 PRs, 20 hours of review, nothing shipped | the error budget; the review gate; "cost per merged change" |
| **Context rot** | agents contradict each other, quality drops in month 2 | `node tooling/src/cli.mjs doctor` weekly; one source of truth per fact |
| **You become the bottleneck** | every task waits for you | move decisions to files; the agents escalate only the six founder gates |
| **Burnout** | the Honghub finding: anxiety, self-doubt, loneliness | take the weekend off; the machine runs without you on purpose; delete one thing weekly |
| **Scope creep from features** | 40 features, 0 users | the kill line; "no feature before a user asked twice" |
| **Security as an afterthought** | an RLS hole or a leaked key | the CI gates on day one, not in month 3 |
| **Nobody can maintain it** | you are the only one who understands the code | the reviewer role; written ADRs; the system stays in files so it is never only in your head |
