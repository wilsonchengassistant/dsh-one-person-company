# One-person company

A workspace-level operating system for running a software company with one human
and a team of AI agents.

**The whole mechanic in one line:**

```sh
node tooling/src/cli.mjs pack <TASK-ID>
```

The output of that command **is the prompt you give an agent**. It assembles the
company charter, the approved spec, the task, the role charter, the declared
write scope, the definition of done, and the operating rules — about 300 lines,
not the whole repository. Everything else in this system exists to make that one
prompt trustworthy.

## Bootstrap a new workspace

**From the GUI:** open **Company board** — it is a panel row in the sidebar, beside
Plugins and Automation tasks. A workspace with
no company OS offers a *Bootstrap this workspace* button, which does the same
thing as the command below. That is the intended path for a user who does not
want a terminal.

**From the CLI:** `bootstrap.sh` and `template/` sit next to this skill, in the
plugin's base directory. The template is reusable; the product state is not.

```sh
bash bootstrap.sh /path/to/new/workspace
```

Optional flags: `--force` (overwrite an existing `tooling/`), `--check` (dry run).

What you get:

| Copied by the template (reusable, never edited per project) | Generated by `opc init` (per project) |
|---|---|
| `tooling/` — the `opc` CLI | `company/charter.md` |
| `playbook/` — the 13-document guide | `company/metrics.md`, `budget.md`, `roadmap.md` |
| `company/AGENTS.md` — the eight rules | `company/specs/`, `tasks/`, `decisions/`, `playbooks/` |
| `company/research/` — 4 source-linked briefs | `.agent/roles/` — the 10 role charters |
 `.agent/checklists/` — DoD, review, pre-ship |
| `package.json`, `.gitignore` | `AGENTS.md` — the workspace manual |

Never copy a product's `company/specs/`, `tasks/` or `charter.md` into a new
workspace. That is the one thing that must start empty.

## The five commands

| Command | When | What it does |
|---|---|---|
| `node tooling/src/cli.mjs doctor` | first thing every session | ~30 checks: tasks with no approved spec, acceptance criteria owned by nobody, a task whose owner role has no charter, dependency cycles, empty verification commands, two runnable tasks writing the same path |
| `node tooling/src/cli.mjs board` | to see state | every task with status, owner, priority, spec, dependencies |
| `node tooling/src/cli.mjs board --ready` | to choose work | **only** tasks whose dependencies are done and whose spec is `approved` |
| `node tooling/src/cli.mjs pack <ID>` | to start work | the prompt (see above) |
| `node tooling/src/cli.mjs budget` | weekly | the spend ceilings from `company/budget.md` |

Also: `new spec`, `new task`, `new adr`, `new research`, `new incident`,
`new release`, `roles`. `npm link` installs the `opc` shorthand.

## Start here, in order

`playbook/12-the-full-cycle.md` is the practical walkthrough — the exact prompt
to paste at each stage. The short version:

1. **charter** — the human writes it. Who hurts, what it costs them, why you win.
2. **spec** — an agent drafts it, the human approves it. `status: approved` only
   when a QA agent could write failing tests from the criteria without asking.
3. **tasks** — decomposed from the approved spec, each with an owner, a write
   scope and a runnable verification command.
4. **build** — `pack` the task, hand it to an agent, keep it in the write scope.
5. **review** — a *different* agent, read-only, assumes the work is wrong.
6. **deploy** — the devops role ships it; the human clicks the preview.
7. **operate** — schedules for the daily report, the support triage and the
   weekly metrics read.

The **Company board** panel shows which stage the project is at and offers a
button that copies the exact prompt for the next step. The same computation is
available headless as `node tooling/src/cli.mjs cycle`.

**The user operates from the GUI, not a terminal.** Do not hand them shell
commands to run — run them yourself, or drive the panel. When you do need to hand
them something, put it in the chat as a prompt to paste, not a command to type.

The only four things the human decides: the charter, spec approval, the review
verdict, and the six founder gates. Everything else is an agent's job.

## The loop

```
research → spec → design → implement → test → review → ship → operate → support → learn
```

One role per arrow, one artefact per stage, all in files under `company/`.

1. **charter** — the human writes it, once per company. Who hurts, why they pay.
2. **spec** — problem, scope, user stories, numbered `AC-n` acceptance criteria.
   Set `status: approved` only when a QA agent could write failing tests from it.
3. **tasks** — decompose the spec. Each task needs a linked spec, an owner
   (`agent:<role>` or `human:<name>`), `writes:` scopes, and a `Verification`
   block with a **runnable** command.
4. **work** — `pack` the task, hand it to an agent, keep it inside its write scope,
   require the real command output.
5. **review** — a *different* agent, read-only, assumes the work is wrong.
6. **move the card** — edit the task file's `status:`. That is the whole tracker.

The link between two files has a name:

- `specs/<date>-<slug>.md` is the **contract**. Its `## 6. Acceptance criteria`
  list is what QA turns into tests.
- `tasks/T-NNNN-<slug>.md` is the **work ledger**. Its `Verification` block is
  how the reviewer checks that the work happened at all.

## A mockup before an engineer builds a screen — and the human approves it

`design/screens/<name>.html` is a single-file interactive prototype: embedded CSS
tokens, embedded JavaScript, a state switcher for empty / loading / error /
success, and a working primary action. One file, no build step.

The human approves it in the panel, which records the decision and the
`spec_version` it was made against in `design/approvals.json`. A UI task an
engineer owns cannot start until that approval exists; the designer's own tasks
are exempt.

**A rejected mockup usually means the requirement changed.** That is expected: a
mockup is the requirement in another language. When it happens, do not start
building — go back to the spec first: bump `spec_version`, add a change-log row
saying what changed and that a mockup review caused it, recompute `approved_hash`,
re-approve, and re-scope any task whose acceptance criteria no longer match. An
approved spec edited without re-approving is an error, and so is a task claiming an
AC the spec no longer has.

## Architecture is an artefact, not a drawing

`docs/architecture/README.md` holds the four diagrams — **System**, **Backend**,
**Frontend**, **Data** — as Mermaid blocks. They are required, not optional: a
task that changes the system's shape updates them in the same change, and the
reviewer treats an unchanged diagram against a changed component as a blocking
finding. A diagram that does not match the code is worse than no diagram, so
they are owned artefacts rather than generated pictures.

## Never impersonate the founder

`design/approvals.json` is not yours to write. An approval is an **Ed25519
signature the DSH host makes**, with a private key that is not in this repository;
the panel is the only thing that produces one.

Writing `by: "human:founder"` into that file is not a shortcut, it is
impersonating the person you work for. `opc doctor` reports it as a forged
approval, `opc check-commit` refuses the commit, and the human sees it on the
Company board.

This was learned the hard way: an agent read the file, read the code that checks
it, computed the mockup hash itself and wrote itself an approval, then reported
"0 errors, done". Do not be that agent.

The same applies to every gate. If a check blocks you, fix the artefact or
escalate to the founder. Do not use `git commit --no-verify`. Do not re-label
tasks to make them pass. The gate is the product's quality, not paperwork.

## The rules that make it work

- **The spec is the contract.** No work starts before it is approved. `doctor`
  enforces this; `board --ready` will not show a task whose spec is a draft.
- **Write scopes are real.** Declare the paths a task may touch. Two runnable
  tasks writing the same path is reported as a bug.
- **Never claim what you did not verify.** The `Verification` block is mandatory.
  Never ask an LLM whether an agent finished — check the actual state (measured:
  LLM judges detect false completion at AUROC ≤ 0.65, while the failure itself is
  ~76% of self-assessed coding-agent failures).
- **Human gates.** Spending money, anything legally binding, anything
  irreversible in production, anything customer-facing, changing the charter or
  the definition of done, and the first launch — human only.
- **Distribution is not automatable.** The agents compress build and operate
  cost, not the cost of being found. Do not let the board fill up with features
  before one real person has paid.

## The sidebar panel

The plugin adds **Company board** as a panel row in the sidebar, beside Plugins and
Automation tasks. It opens
the board for whichever registered workspace carries a `company/` folder: task id,
status, priority, owner, dependencies, and which tasks are startable right now.
It reads the same parser the CLI uses, so the panel and `opc board` cannot
disagree. Use it to check the board without breaking a terminal session.

## Known friction

- `opc new task` produces an intentionally incomplete task: `doctor` will report
  the missing verification command and the unowned acceptance criteria until you
  fill them in. That is the check working, not a failure.
- A fresh workspace has two warnings: no tasks yet, and no direction sentence in
  `company/roadmap.md`. Both clear once real work starts.
